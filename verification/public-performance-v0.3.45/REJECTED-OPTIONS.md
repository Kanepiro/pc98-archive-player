# 不採用の方法

## モード1〜3の逐次デコード

ULTIMATE IIのVideoSampleSink → MediaStreamTrackGenerator → HTMLVideoElement経路を独立候補で検証した。参考1080p/24fps短尺ではTSLが一致したが、Linux Chromiumの320×180/15fps素材ではモード1が不一致だった。同じ33フレーム・15608バイトでもSHA-256は以下のとおり。

- 公開版: 4cba4167bc0781abe197fbd2c4c327b4fee4892a37373bd89895ff99927a41c0
- 逐次取得候補: e5ee404bedc4b11dd9bdae6a03ce3e708e4852bea3407a86d06bee574e618cc4

HTMLVideo seekへ戻した候補では一致。この移植はWindows/Web両候補から外した。特定素材の一致を汎用性の根拠にしない。最終構成ではモード1〜3を従来の直列取得に戻し、独立したフレームを扱うモード4のCanvasSinkだけで1フレーム先読みを使用する。正確なデコーダー内部の色変換・時刻差の特定までは行わず、不一致が出る経路を採用対象から外した。

## その他

- モード2の新WebGPU移植: ULTIMATE IIでフレーム1087の不一致が記録されており、再導入しない。
- GPU Gaussian blur: 丸め差のある実験経路を移植しない。
- 近似候補絞り込み、文字数・密度削減: 不採用。厳密な下限とビット一致キャッシュのみを扱う。
- 特定CPU命令、固定6スレッド、GPUクロック強制、電力設定変更: 不採用。
- 専用版のlossless NVENCやAAC stream copy: 公開版エンコード仕様を保持するため移植しない。
- 専用版を公開版の代用とすること、GitHub/Vercelの公開差し替え: 実施しない。

初期試作の結果は最終版の代表値に含めない。試作・失敗ログは最終測定とは区別する。

## HTMLVideoの取得と変換の重複実行（長尺検証で撤回）

初回のWindows長尺モード3でフレーム2160（90秒）と2161（90.05秒）のTSLに差が出た。2160は公開版の直前フレームと一致し、古い動画フレームを取得したことと整合する。短い境界区間の12試行では再現せず、長尺全体の実行条件で発見された。

同じ候補のGPU計算を維持したままHTMLVideoの先読みを止めると、2,880フレーム全体のTSL SHA-256が公開版と一致した。ブラウザー内部の原因を断定せず、競合し得る取得・変換の重複を全モード1〜3で撤回した。モード4のCanvasSink方式は維持。初回候補の速い値は最終中央値へ混ぜず、影響するWindowsモード1〜3とWeb全56試行を再測定した。

不一致: 72c73e4125c83bb39ca6b584afa507755aaf89c52e125b46fc397d00896d827d

公開版／先読みなし: 650b3b320b6b324e2dce0fae0ebbf55880799e827d7fb6d9e1acc01482906e78

診断試験の変換時間は約514秒（公開版約1,282秒）。診断用計測は正式中央値と分ける。不採用候補のWindows 18試行、初回Web記録、当時のソースと診断ログはWindows検証ZIPのrejected記録に保存する。
